# `research/measurement/`

Reproducible audits of public chess data, run to try to **break** a candidate measurement rather
than to support it. Nothing here runs in the product, nothing here is imported by `client/`,
`server/` or `shared/`, and the bundle budget is unaffected.

Read [`docs/measurement/GO_NO_GO.md`](../../docs/measurement/GO_NO_GO.md) first; it says what these
scripts concluded and what may not be claimed from them.

## Order of writing, which is the methodology

1. `predicates.py` — the trigger definition. **Written and hashed before any Lichess label was
   read.** Board geometry and legality only; no engine, no SEE, no theme.
2. `scan_games.py` — walks 60,000 unfiltered rated games and applies (1).
3. `scan_puzzles.py` — applies the same unmodified (1) to puzzle positions, **then** joins the
   themes. Separate file so the ordering is visible in the repository rather than asserted.
4. `oracles.py` — SEE and Stockfish, each writing its own field. No oracle may set `trigger_state`.
5. `enrich.py` — adds the oracle columns to a scanned corpus.
6. `analyse.py`, `narrow.py`, `definition_variance.py` — the falsification runs.
7. `sdt.py` → `sdt.ts` — `PORT_AFTER_EQUIVALENCE`; the fixture in `equivalence/` is generated by
   the Python and `tests/research/measurement-sdt.test.ts` asserts the port reproduces it.
8. `negative-controls.ts` — eight false claims, each of which must fail for its own reason.

## What runs in CI

`sdt.ts` and `negative-controls.ts`, via `npm test`. The Python is not run in CI: it needs 320 MB
of downloaded corpora and a Stockfish binary, and a check that cannot run is worse than one that
is honestly out of band. What CI *does* guarantee is that the arithmetic the Python used is still
the arithmetic the controls run on.

## Results

`results/` holds the JSON the register quotes, at 64 KB. The corpora themselves are not vendored;
`docs/measurement/ITEM_BANK_PROTOCOL.md` has the download URLs, byte sizes and exact commands.
